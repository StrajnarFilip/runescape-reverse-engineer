D4 - Melee rotation engine
==========================

:Status: done
:Wave: 1
:Branch: ``telos/D4``
:Kind: Python

Shared rules and procedure: ``../README.rst``.

Goal
----

Choose the next offensive ability. A small engine evaluates data-driven
priority lists per phase against cooldowns, GCD, adrenaline, buffs and
equipment match. The first rotation is simple and forgiving; it is not the
PVME speedkill.

Read first
----------

* ``docs/telos-melee-research.rst``, sections "Current combat rules and legacy
  material" and "Melee rotation reference".
* ``docs/inventory-and-abilities.rst``, section "Ability requirements and
  readiness".
* ``profiles/ability_bindings_951_3.json``.
* S0a contracts.

Owns
----

* ``python/rs3_reader/bot/rotation.py``
* ``profiles/rotations/`` (one file per phase)
* ``tests/python/test_bot_rotation.py``

Depends on
----------

S0a. Uses P3 effects and P5 action-bar bindings when present; until then
conditions on unknown buffs evaluate as not met, and bindings come from a
hand-written section of the rotation profile.

Delivers
--------

Ability intents at the lowest priority, at most one per GCD, naming the rule
that fired. An ability whose timer is unmapped or whose equipment match is
unknown is never selected. Removed pre-modernisation abilities are not
referenced.

Done when
---------

Replay and scenario tests show a legal ability is proposed whenever one is
ready and the GCD is free, nothing is proposed during the GCD, and each phase
file loads and validates against the ability bindings.

Needs the user
--------------

The intended gear, weapons and unlocked abilities, written once into
``profiles/rotations/``. Live use starts at rung 4 of track L.

Implementation and verification (2026-11-13)
------------------------------------------

``RotationEngine.step(WorldState)`` proposes one ROTATION-priority GCD intent.
Five conservative phase files validate against a canonical SHA-256 of the
ability definitions. Unknown IDs, inactive legacy definitions, duplicate rule
IDs and changed definition metadata reject configuration. No removed ability
is present in the shipped phase policies.

Every rule requires known zero GCD and ability cooldown, full castable=True,
allowed equipment match, a fresh melee weapon and living selected NPC, explicit
phase, known adrenaline and a validated key binding. Adrenaline thresholds are
reserve policies, not inferred raw-cache costs or old activation floors.
Unknown buff conditions fail; a partial buff list cannot establish absence.
Phase 4 omits the channel rules. These are forgiving baselines, not PVME
speedkill scripts or live-validated phase-5 tactics.

P5 observed ability chords override the manual profile section. A changed,
unmapped or ambiguous observed bar blocks selection rather than falling back
to a stale manual key. Only P5's currently decoded function-key forms are
translated; game modifier codes are not native masks. ``can_send`` rechecks
phase, gear, target, buffs and the chosen chord before D6 dispatch.

``note_sent`` records accepted input only. A newer positive cooldown on the
selected ability acknowledges it; GCD alone does not. Timeout latches a fault.
``note_rejected`` never advances resource/buff state. ``create_stack`` is a
proposal-only S0a adapter and imports no native input code.

The intended setup and all handwritten keys remain explicitly unconfigured,
as the user deferred live setup. Runtime native castability is currently null,
so current captures do not generate offensive casts. Fourteen D4 tests pass,
including all five phase profiles, legal synthetic readiness, unknown fields,
buffs, equipment, changed bars, confirmation and a golden no-input replay of
the native-hit capture. The Windows x64 Release build and all 10 CTest suites
passed (92 Python tests).
