A1 - Actuator backends
======================

:Status: done
:Wave: 1
:Branch: ``telos/A1``
:Kind: Python (Arduino sketch if needed)

Shared rules and procedure: ``../README.rst``.

Goal
----

Implement the S0a ``Actuator`` interface twice: over the existing foreground
input functions in the DLL, and over the Arduino Leonardo serial protocol,
which has a sketch but no host-side driver.

Read first
----------

* ``python/rs3_reader/bot/actuator.py`` from S0a.
* ``include/rs3/rs3.h`` (foreground input section), ``include/rs3/combat.h``
  (``rs3_set_prayer``), ``src/input.c``, ``tests/native/test_input.c``.
* ``docs/arduino-keyboard.rst``, ``arduino/serial_keyboard/serial_keyboard.ino``.

Owns
----

* ``python/rs3_reader/bot/actuator_sendinput.py``
* ``python/rs3_reader/bot/actuator_serial.py``
* ``arduino/serial_keyboard/``, ``docs/arduino-keyboard.rst``
* ``tests/python/test_bot_actuator.py``

Depends on
----------

S0a.

Delivers
--------

Two interchangeable backends with: a serialized queue, a per-tick action
budget, rejection of intents whose deadline has passed or whose snapshot is
stale, and release of every held key on fault or shutdown. The serial sketch is
keyboard-only today; state in the brief's Requests what pointer support the
movement track (A2) will need rather than guessing.

Done when
---------

Both backends pass the same test suite against a fake device and a fake DLL,
including the fault path, without the game running. The serial driver uses the
standard library only.

Needs the user
--------------

No user input was needed for software acceptance. The Release build and all
10 CTest suites passed on 2026-11-13 (97 Python tests, including 19 A1 tests).
Both backends were exercised with fake devices; the actual sketch also passed
host compilation/parser/DTR/watchdog tests. No game input was sent.

Optional hardware validation remains: compile/upload for Arduino Leonardo,
open a text editor, assert DTR and send HELLO, TAP 04, then RELEASE_ALL. Confirm
one key arrives and disconnecting clears held keys. Actual AVR compilation
and physical USB delivery have not been tested. Instructions and guarantees
are in ``docs/arduino-keyboard.rst``.

Requests
--------

* Native input owner: add an additive, guarded, balanced key-tap API accepting
  modifiers and a fresh snapshot, with existing partial-input cleanup. The
  current DLL exposes modified prayer and unmodified ability input only.
  Generic item and modified ability intents explicitly reject in the native
  backend until this API lands. No C files were changed by A1.
* P2/L update, 2026-11-14: the original profile now supplies a guarded received
  server-tick ordinal in WorldState. A1 still rejects an unknown/stale index.
  Tick phase and input-arrival timing remain unknown; this mapping alone does
  not enable input or prove which server tick will process a chord.
* A2: pointer operations require calibrated client coordinates, visible-window
  and bounds checks, and a mouse-capable serial protocol/device or a declared
  native-pointer route. The Leonardo sketch remains keyboard-only and both A1
  backends reject pointer intents. Do not encode movement as guessed keys.
* P5/D6: translate game modifier codes to the native Ctrl=1/Shift=2/Alt=4 mask
  and pass fresh, validated account-specific bindings. Letter/digit HID usages
  require keyboard-layout calibration. D3/D4/D6 retain castability and cooldown
  policy; accepted device input needs later observation to acknowledge it.
